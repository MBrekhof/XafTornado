## Findings

### 1. Critical - Blazor AI tool execution bypasses XAF security entirely

Evidence:
- `AIToolsProvider.GetObjectSpace` creates a non-secured object space for Blazor via `INonSecuredObjectSpaceFactory.CreateNonSecuredObjectSpace(...)`: `XafTornado/XafTornado.Module/Services/AIToolsProvider.cs:112-140`
- The data-reading and data-mutating tools all use that helper:
  - `query_entity`: `XafTornado/XafTornado.Module/Services/AIToolsProvider.cs:390-395`
  - `create_entity`: `XafTornado/XafTornado.Module/Services/AIToolsProvider.cs:502-576`
  - `get_active_view` record reload: `XafTornado/XafTornado.Module/Services/AIToolsProvider.cs:670-673`
  - `update_entity`: `XafTornado/XafTornado.Module/Services/AIToolsProvider.cs:815-917`

Impact:
- In the Blazor app, AI-driven reads and writes are not constrained by the current user's XAF permissions.
- A user who should only see a subset of entities or records can potentially query or modify anything the database model exposes.

Recommendation:
- Use secured object spaces for user-facing AI actions.
- If a non-secured path is needed for internal tasks, isolate it behind an explicit server-only boundary that is never reachable from end-user prompts.

### 2. Critical - The test API is always mapped and has no authorization barrier

Evidence:
- The controller is described as "Only intended for development/testing" but is compiled normally and exposes `tool`, `ask`, and `clear` endpoints: `XafTornado/XafTornado.Blazor.Server/Controllers/TestApiController.cs:12-95`
- There is no `[Authorize]`, environment check, or feature flag on the controller.
- Controllers are always mapped in the main pipeline: `XafTornado/XafTornado.Blazor.Server/Startup.cs:141-146`

Impact:
- `/api/test/tool` can directly invoke AI tools, including record creation and updates.
- `/api/test/ask` exposes the full prompt-to-tool loop remotely.
- Because the controller is anonymous, this becomes an unauthenticated remote mutation/query surface, not just a developer convenience endpoint.

Recommendation:
- Remove the controller from normal builds, or gate it behind `env.IsDevelopment()` plus strong authentication/authorization.
- If it must exist, put it behind an explicit test-only startup path and disable it in production artifacts.

### 3. Critical - Per-user Blazor state is stored in singletons, causing cross-user leakage and races

Evidence:
- AI state is registered as singletons: `XafTornado/XafTornado.Module/Services/ServiceCollectionExtensions.cs:16-31`
- Blazor navigation service is also singleton: `XafTornado/XafTornado.Blazor.Server/Startup.cs:33-37`
- `AIChatService` keeps mutable conversation history and model selection in instance fields: `XafTornado/XafTornado.Module/Services/AIChatService.cs:30-37`, `XafTornado/XafTornado.Module/Services/AIChatService.cs:121-128`, `XafTornado/XafTornado.Module/Services/AIChatService.cs:191-221`
- `ActiveViewContext` stores mutable active-frame and current-record state in a singleton: `XafTornado/XafTornado.Module/Services/ActiveViewContext.cs:5-57`
- The model selector mutates the shared `AIChatService` instance: `XafTornado/XafTornado.Module/Controllers/SelectAIModelController.cs:82-86`

Impact:
- One user's chat history can bleed into another user's prompts.
- One user's model switch changes the model for all users.
- Active view, navigation, save, close, and refresh requests can target the wrong user's frame or view.
- `AIChatService._history` is a plain `List<T>` with no synchronization, so concurrent requests can interleave or fail unpredictably.

Recommendation:
- Move user-specific AI, navigation, and view-context services to a per-circuit/per-session lifetime.
- Treat chat history and active-frame references as per-user state, never application-wide state.

### 4. Medium - The project has effectively no automated regression suite

Evidence:
- `XafTornado.Tests` is a console application, not a test project: `XafTornado/XafTornado.Tests/XafTornado.Tests.csproj:1-11`
- Its entry point is a YAML-driven runner that requires a manually running app instance: `XafTornado/XafTornado.Tests/Program.cs:7-53`
- The advertised `playwright` step is a stub and does not execute browser automation: `XafTornado/XafTornado.Tests/TestRunner.cs:144-145`
- `dotnet test XafTornado.slnx --no-build` completed without discovering tests.

Impact:
- CI cannot catch regressions in the AI tool layer, security boundaries, navigation behavior, or schema tooling by default.
- The existing runner is useful as a manual harness, but it is not a substitute for repeatable automated tests.

Recommendation:
- Add real `dotnet test` projects for unit/integration coverage.
- Either implement the Playwright path fully or remove the unsupported step type to avoid a false sense of coverage.

### 5. Medium - Configuration and dependency hygiene are not ready for a stable deployment pipeline

Evidence:
- Tracked configs contain hard-coded database passwords:
  - `XafTornado/XafTornado.Blazor.Server/appsettings.json:2-4`
  - `XafTornado/XafTornado.Win/App.config:28-30`
- A static signing key is stored in tracked config: `XafTornado/XafTornado.Blazor.Server/appsettings.json:32-35`
- The module project mixes explicit Roslyn 5.0 references with transitive packages expecting 4.10, which produced `NU1608` warnings during build: `XafTornado/XafTornado.Module/XafTornado.Module.csproj:31-33`
- Multiple packages use floating versions, which makes restores non-reproducible:
  - `XafTornado/XafTornado.Module/XafTornado.Module.csproj:42`, `XafTornado/XafTornado.Module/XafTornado.Module.csproj:45`
  - `XafTornado/XafTornado.Blazor.Server/XafTornado.Blazor.Server.csproj:27`
  - `XafTornado/XafTornado.Tests/XafTornado.Tests.csproj:10`

Impact:
- Secrets and default credentials are easy to reuse accidentally outside local development.
- Build behavior can drift over time depending on what package versions happen to resolve.
- The current warning state makes dependency issues easier to miss in future builds.

Recommendation:
- Move secrets and connection strings to user secrets or environment-specific secret storage.
- Generate unique signing keys per environment.
- Pin package versions and align Roslyn package versions with the transitive dependency graph.

## Conclusion

The project has a workable prototype structure, but it is not safe for multi-user or production-style Blazor deployment in its current form. The two issues to address before anything else are the authorization boundary around AI execution and the use of singleton services for per-user state. After those are fixed, the next priorities are establishing real automated tests and tightening configuration/dependency management.
